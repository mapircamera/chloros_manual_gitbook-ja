# マルチカメラアレイ

LATTICE **アレイ**とは、2台以上のLATTICEカメラを1つの同期ユニットとして接続したものです。そのうち1台のカメラが**マスター**となり、共有の同期ライン（デフォルトは**Line2**）上でハードウェアGPIOトリガーパルスを発信します。 これにより、すべての構成カメラが同じ瞬間の画像を撮影します。Chlorosは、PTPタイムシンク、ライブプレビュー（カメラごとのタイル表示または位置合わせ済みの単一マルチバンド合成画像）、および同期撮影機能を追加します。各撮影パスでは、すべてのカメラが同じタイムスタンプとフレームIDを共有する1つの**フレームグループ**が生成され （キャプチャ出力では`fid:N`として報告されます）。

アレイは、モノクロ（M3M）カメラが植生指数を生成する仕組みです。1台のカメラが1つのバンドを提供し、アレイがそれらをマルチバンドスタックとして整列させます。 [モノカメラと植生指数](mono-indices.md)を参照してください。

アレイを接続するには 3 つの同等の方法があり、いずれも同一の「smart-prep」フローを実行します：

| インターフェース | 開始点 |
| --- | --- |
| GUI | [Cameras] タブ → **Connect Array**（青いボタン） |
| CLI | `chloros-cli lattice array-connect --serials SN1,SN2,…`（最初のシリアル番号 = マスター） |
| Python SDK | `connect_array(serials=[…])` → `ArraySession` (最初のシリアル番号 = マスター) |

Smart-prep では、ネットワーク機能プローブ（ICMP DF ピング + GVSP プローブ）、同期層の選択、要求されたフレームサイズでのフレームレート予測、パックされた 12 ビット転送の決定 （[12ビットパケット転送](#packed-12-bit-transport)を参照）、PTP有効化、カメラごとのピクセル形式の自動選択、各カメラの保存済み状態からの自動露出シード、およびLine2でのGPIOトリガー設定。

**デフォルトではフルセンサー （1.3.0での新機能）。** Connectは、ユーザーが指定したフレームサイズ（2048×1536のフルセンサー、ビニングやクロップなし）を維持し、ユーザーが別段の選択をしない限り — フレームレートはホストとネットワークが提供する値に合わせて低下します。Connectが独自にビニングやクロップを行うことはありません（バージョン1.2.0では、1.5 fps未満の場合に自動的にビニングが行われていました）。 ビニングやより小さなROIの選択はユーザー次第です。接続ダイアログでいずれかを選択すると、「予測結果」にその結果となるフレームレートが表示されます。また、`array-connect`コマンドを実行すると、より高速なオプションとその予測フレームレートが出力されます。

{% hint style="info" %}
これらの機能が動作するには、リンク上でカメラに到達可能である必要があります — [カメラの接続](connecting.md)を参照してください。マルチカメラリグの場合、リンク速度と同様にホストNICの受信リング設定も重要です。症状と解決策の完全な一覧は、[CLIリファレンス § ホストNICの設定と調整](../reference/cli-reference.md#host-nic-setup--tuning-lattice-arrays)に完全な「症状→解決策」表が記載されています。
{% endhint %}

## [アレイ接続] ダイアログ

[カメラ] タブ → **[アレイ接続]**を選択すると、3 ステップのウィザードが開きます：**[選択] → [表示モード] → [設定]**。

### ステップ 1 — マスターとスレーブの選択

<!-- SCREENSHOT-NEEDED: Array Connect dialog, Select scene, with 3-4 LATTICE cameras discovered (an FRGB among them). Table showing Camera / Serial / IP / Master radio / Slave checkbox columns in camera order (M3C first, FRGB at the top), with the FRGB pre-selected as master and the green "Sync cable found on N cameras. Any of them can be master; the RGB camera (else the first) is pre-selected." probe banner visible above the table. -->



ダイアログが開くとすぐにネットワークのスキャンが開始され（「ネットワークをスキャン中...」）、続いて同期ケーブルの検出が行われます（「同期ケーブルを検出中...」）。これにより、M8 同期ライン上にどのカメラがあるかが特定されます。アレイを構築するには、少なくとも **2 台のカメラ** が必要です。

M8同期ケーブルは1つの分岐点で合流しているため、**ケーブル接続されたカメラならどれでもマスターになることができます**となります。プローブは役割を事前に設定します — RGB（`-FRGB`）カメラが接続されている場合はそれをマスターとし、そうでない場合は最初に接続されたカメラをマスター、その他の接続されたカメラをスレーブとします — そして、以下の3つのバナーのいずれかを表示します：

| バナー | 意味 |
| --- | --- |
| 「{n}台のカメラで同期ケーブルを検出。いずれのカメラもマスターに設定可能。RGBカメラ（それ以外の場合はリストの最初のカメラ）が事前選択されています。」（緑） | プローブが同期ライン上のカメラを検出しました。「マスター」および「スレーブ」のチェックボックスには既にチェックが入っています。 |
| 「マスターが検出されません - GPIOケーブルを確認してください」（オレンジ） | どのカメラもトリガーパルスを検知していません。同期ケーブルの接続を確認してください。役割は依然として事前設定されています（RGBカメラ、それ以外の場合はリストの最初のカメラがマスターとして設定されています）が、変更可能です。 |
| 「同期ケーブルなし：{serials}」（オレンジ） | リストされたカメラには同期ケーブルが接続されていません。 |

カメラテーブルには、**カメラ / シリアル番号 / IP / マスター（無線） / スレーブ（チェックボックス）**という列があります。行は**カメラの順序**で表示されます — M3C（バイヤー）カメラが M3M（モノクロ）カメラより先に表示され、M3C の中では FRGB、FRGN、FOCN、FNGB の順で表示されます。 M3Mカメラはフィルター波長順で、最も低い波長から先に表示されます（F450がF808より先）。サイドバーのカメラリストとグリッドのデフォルトレイアウトは、同じ順序を採用しています。

* **1つのマスター**と**1つ以上のスレーブ**を正確に選択してください。現在のマスターのラジオボタンを再度クリックすると、選択が解除されます。別のマスターを選択するには1回のクリックで済みます。新しいマスターがスレーブを離れ、以前のマスターはスレーブになります（同期ケーブルがない場合を除く）。
* **「No Sync Cable」**とマークされたカメラは、スレーブとして選択することはできません。トリガー配線のないスレーブは、同期ラインを永遠に待ち続け、無効な映像を送信してしまうためです。そのカメラは、代わりにスタンドアロンカメラとして接続してください。
* すでにスタンドアロンとして接続されているカメラは *無効化されません*：アレイ接続を行うと、スタンドアロンセッションが解除され、カメラがアレイ内で再起動します。

**次：表示モード →**は、マスターと少なくとも1台のスレーブが選択されると有効になります。**再スキャン** を選択すると、検出と配線プローブが再実行されます。

{% hint style="warning" %}
**キャンセル**は、スキャンまたはプローブの実行中は無効になります。プローブ実行中にキャンセルすると、LATTICEカメラのファームウェア上でカメラSDKがクラッシュする可能性があります。プログレスインジケーターが完了するまでお待ちください。
{% endhint %}

### ステップ 3 — アレイ設定と予測される結果

<!-- SCREENSHOT-NEEDED: Array Connect dialog, Settings scene, healthy state: left column with ROI / Binning / Trigger Rate / Wire Budget controls (1.3.0 has no "Pin resolution" checkbox), right "Projected Outcome" column showing green "Simultaneous capture" tier, an fps range, the NIC line, the "Sim-emit burst" line, and the "Wire budget" line with a checkmark. -->



このシーンに入ると、Chlorosはバックエンドに**推奨設定**を問い合わせ、それを適用します。それは、ホストと通信回線が提供するレートにかかわらず、**フレームレートが許す限り、ビンニングやROIクロップを行わないフルセンサー**を使用するというものです。フルセンサーに対応できるレートが一切ない場合にのみ、推奨設定はフレームを縮小し、 その場合、ビニングは視野全体を維持できるため、ROIクロップよりも優先されます。そこから先は、解像度とフレームレートのトレードオフとなります。設定を変更するたびに、分析がリアルタイムで再実行され、右側の**予測結果**パネルが更新されます。

左の列 — 設定：

| 制御 | 選択肢 | デフォルト | 備考 |
| --- | --- | --- | --- |
| **ROI（視野）** | フル (2048×1536) / ハーフ (1024×768) / クォーター (512×384) | フル | センサーのトリミング：ネイティブピクセルピッチで、より小さな領域にハーフ／クォーターにトリミングします。 |
| **ビニング** | 1× / 2×（2×2の合計） / 4×（4×4の合計） | 1× | ハードウェアビニング：2×2 = ワイヤコストの4分の1で全視野（FoV）を実現；4×4 = ワイヤコストの16分の1で全視野（FoV）を実現。 カメラがビニングに対応していない場合は非表示。 |
| **ワイヤ側画像** (読み出し) | — | — | ビニング後の幅×高さで、実際にワイヤ上で送信されるサイズ。16の倍数（最小64）に切り詰められる。 |
| **トリガーレート** | 0.5–60 fps、ステップ 0.1 | 空欄 = 自動 | マスターのトリガー発射レート。 空欄のままにすると、Chlorosが自動的に算出します。 |
| **ワイヤ・バジェット**| 20–2000 MB/s、ステップ 10 | 空欄 = 自動 | ホストが実際に処理できる量（MB/s単位） —**アレイ全体の割り当てがこれに依存する唯一の数値。** ネットワークアダプタから自動検出されます。アレイがフレームの破損を報告する場合は、この値を下げてください。検出された値は、USBアダプタや共有スイッチの能力を過大評価している場合があります。変更すると、予測がリアルタイムで再実行されます。 このフィールドには、前回アレイが接続されていた際のバジェット（プロジェクトに保存されている値）が表示されるため、一度修正したバジェットは保持されます。 |

1.2.0 からあった **ピン解像度** チェックボックスは削除されました。接続時には、選択したフレームサイズが常に維持され、代わりにフレームレートが低下します。

右側の列 — **予測結果**：

* **同期レベル** — 「同時キャプチャ」（緑）、「同時キャプチャ（FTD-時差送信）」（緑）、「時差キャプチャ（100 ms ドリフト）」（黄）、または「構成が大きすぎる」 （赤）。Chlorosは、ワイヤをカメラのペースに合わせて共有できるレートで利用可能な場合は常に「同時キャプチャ」を（各カメラのシェアが縮小するにつれてフレームレートは低下します）、それが不可能な場合にのみ「時差キャプチャ」を選択します。つまり、アレイはどのネットワークでも、そのネットワークが許容するフレームレートで接続されます。
* **fps予測値** — アレイが動作すると予想されるフレームレート。 同時キャプチャの場合、これは単一の数値となります。まずフレームレートが決定され、自動露出がその期間を埋めた後、ゲインが上昇するため、暗いシーンでもフレームレートが低下することはありません（[自動露出による露出時間とゲインの配分方法](camera-settings.md)を参照）。 時差キャプチャの場合、これは範囲（「暗い → 明るい」）として表示されます。これは、暗いシーンでは各カメラの露光時間が長くなるため、時差が拡大するからです。
* **NIC ライン** — リンク速度と持続スループット（「NIC {mbps} Mbps · 持続 {N} MB/s」）。
* **同時送信バーストチェック** — ホストのNIC受信リングは、すべてのカメラからの同時バーストを1つ受け入れることができるか（「同時送信バースト：X MB · NICリング利用可能：Y MB ✓/✗」）。
* **回線予算チェック** — 定常状態の総需要と、衝突防止のための回線上限の比較（「回線予算：{n} 台のカメラによる {demand} MB/s の需要 · 上限 {ceiling} MB/s ✓/✗ オーバーサブスクライブ」）。
* **「この回線上の最大カメラ数：{n} — カメラごとの帯域幅の下限によって設定されるため、ビンニングを行ってもこの数は増えません。」** — カメラ数の上限に近づいている（または超えている）場合に表示されます。
* **「この設定ではフレームがドロップします。"**— バックエンドによる理由が記載された赤い警告に加え、ブロック要因の一覧と青い**解決策の提案**（「このアレイをネットワークに収めるには」／「同時キャプチャを可能にするには」）が表示されます。**適用して接続** は予測結果が存在するまでロックされており、そのラベルには拒否理由が表示されます：

| ボタンラベル | 意味 | 実際に役立つ対処法 |
| --- | --- | --- |
| 「分析中...」 | 分析がまだ進行中。 | 待機。 |
| **「このネットワークにはカメラが多すぎます"**| ネットワーク回線が、1台ずつでもこのアレイを処理できない（集計チェックに失敗）：処理可能なペースをはるかに超えるカメラ数、または他のカメラがストリーミング中。 | カメラ数を減らす、エンドツーエンドでジャンボフレームを使用する、またはより高速なNICを使用する。**ROIを小さくしても解決しません** — 下記を参照。 |
| **「ROIを縮小して有効化」** | この設定ではフレームがドロップします（バースト/リングチェックに失敗）。 | ROIを縮小する、ビニング率を上げる、またはNICの受信リングを修正する。 |

接続中に、シリアル番号ごとの進行状況バーが付いた緑色の**キャリブレーションダウンロードパネル**が表示される場合があります。マシンにカメラを初めて接続する際、ChlorosはGigE経由でカメラから約3.8 MBの工場出荷時キャリブレーションパックを取得します（カメラ1台あたり約70秒）。 キャッシュ済みのカメラではこのパネルは表示されません。カメラが6台を超える場合、行がスクロールします。[カメラの接続](connecting.md)を参照してください。

### パック化された12ビット転送

12ビット形式（`BayerRG12`、`Mono12`）は通常、16ビットワードとして転送されます。**パック**転送では、同じ12ビットを1ピクセルあたり1.5バイトで送信し、ホスト側で展開するため、各フレームの送信時間が25％短縮されます。センサーをフル稼働させた場合、1秒あたりのフレーム数が約3分の1増加します。**保存されるデータは同一です。** Array Connectはこれを自動的に決定します（`auto`）：パッキングが有効であり、かつホスト側にアンパック処理に充てられる余剰CPUリソースがある場合にのみパッキングを行います。GUIにはこの設定を切り替えるスイッチはありません。CLIからは`array-connect --packed {auto,on,off}` （デフォルトは `auto`）を使用してください。8 ビットおよび 16 ビット形式は、決してパックされません。

## 帯域幅：接続可能なカメラ数

アレイが処理できる容量は、Chlorosの仕様ではなく回線の特性によるものであるため、計画に必要な数値はハードウェアマニュアルに記載されています：**[アレイの帯域幅計画](https://mapir.gitbook.io/lattice-camera/setup/array-bandwidth-planning)**。

Chlorosがこれらをどのように扱うか：接続ダイアログはネットワークプローブを実行し、達成可能なフレームレートを予測して、それに適合するティアを選択します。アレイはどのネットワークでも接続可能です。低速なリンクでは、アレイが拒否されたりフレームが縮小されたりするのではなく、各カメラが回線の割り当て分に合わせてペース調整され、フレームレートが低下します。 その回線が一度に1台のカメラさえ処理できないアレイのみが拒否され（**このネットワークにはカメラが多すぎます**）、パケットが黙って破棄されることはありません。詳細は前述の「予測結果」パネルを参照してください。

## フレームが欠落する場合

公開されたグループからカメラが欠落する原因は、まったく異なる2つの理由が考えられます。
そして、それぞれに対処法も正反対です。Chlorosは、これらを区別してカウントし、
どちらの原因も特定できない単一の「不完全」な数値を報告することはありません：

| 発生した事象 | 意味 | 確認すべき箇所 |
| --- | --- | --- |
| **破損**— フレームは到着したが構造的に破損していた | ネットワーク経路上のGVSPパケット損失 |**回線帯域**、NICの受信リング、ジャンボフレーム、スイッチ |
| **未到着**— フレームが全く届かなかった | カメラが起動しなかった、または何も送信されなかった |**M8同期ケーブル**、同期ライン、全メンバーが起動状態にあるか |

アレイがストリーミングしている間、この内訳は10秒ごとに再評価されます。5％を超えると、
両方の数値が明記されてログに記録され、各カメラごとに破損したバッファは最初に発生した時点で
報告され、その後1分ごとに集計されるため、長時間のセッションでも読みやすくなります。

**「未到着」がゼロの破損フレームがある場合、トリガーとケーブルの同期は完璧**であり、失われたフレームはすべてネットワーク経路上の問題によるものです。解決策は、**Wire Budget**を下げ、
再接続することです。

{% hint style="warning" %}
**トリガーレートを下げても、破損フレームの問題は解決しません。** カメラのパケット
ペーシングは、接続時に一度だけ設定されます。トリガーレートを下げても、バーストが
発生する頻度は変わりますが、バースト自体がネットワーク上に送信される速度は変わりません。 測定対象の4台構成のシステムでは、
トリガーレートを5分の1に下げても変化はなかったが、ワイヤ・バジェットを240から
200 MB/sに削減すると、同じリグの破損率が10.4％からゼロになりました。
{% endhint %}

稼働中のアレイは自身で再計画を行うことはできません。切断して再接続し、接続時の
ピッカーが新しい帯域幅に基づいて動作するようにしてください。

### USBネットワークアダプタの制限

USBイーサネットアダプタは*イーサネット*のリンクレートを公表していますが、実際に
維持できる速度はUSBバスとそのドライバによって制限されます。かつてUSB 10GbEドングルは
約1000 MB/sのスループット — これは実際に測定されたことのない数値でした — そして、その架空の余裕に対して
4台のカメラの処理を調整した結果、フレームの6～18％が破損した一方で、アレイは
依然として正常な目標フレームレートを報告していました。USB接続のアダプターは現在、
WindowsおよびNVIDIA Jetsonでは**200 MB/s**、Linux x86_64では**400 MB/s**に制限されています。この上限はパーセンテージではなく絶対値です。なぜなら、制限要因は
バスそのものだからです。USB 1 GbEアダプタは約80 MB/sの転送速度しか得られず、この制限の影響を受けません。

ホストの速度が上限を確実に上回る場合は、**Wire Budget** を引き上げてその旨を指定してください。

## PTP 時刻同期

フレームの *同期* はハードウェアトリガーによって行われますが、**PTP** (IEEE 1588 PTPv2) はすべてのデバイス間で比較可能な *タイムスタンプ* を提供します。 これはアレイ接続時にデフォルトで有効になります：

* **ChlorosホストバックエンドがPTPグランドマスターを実行します**。LATTICEカメラとDAQ-E光センサーはドメイン0でこれにスレーブとして同期するため、画像のタイムスタンプとDAQスペクトルは同一のクロック（約1 ms）に揃います。
* `--no-ptp`（CLI）を実行すると、ベンチワーク用にこの機能が無効化されます。この場合、カメラ間のタイムスタンプは**比較可能ではなくなります**。
* CLIで同期の状態を確認します：

```bash
chloros-cli time-sync status     # grandmaster state, clock identity, health (OK, or why its packets are not reaching the network)
chloros-cli time-sync peers      # slaves seen (cameras + DAQ-E sensors)
chloros-cli time-sync cameras    # per-camera PtpStatus / PtpOffsetFromMaster / PtpMeanPathDelay
```

[Cameras]タブ自体にはPTPインジケーターはありません。各カメラごとの同期情報は、読み取り専用の**Role**（マスター/スレーブ）、**Sync Line**、およびアレイのCapabilities階層として表示されます。DAQ-EのPTP状態は、[Light Sensors]タブのセンサー詳細に表示されます。

## ライブアレイビューメインフィードエリア

<!-- SCREENSHOT-NEEDED: Cameras tab with a connected combined array: sidebar showing the ARRAY row (color badge, array name, "DAQ · on" pill) with indented member camera rows in camera order (M3C before M3M, monos by wavelength), and the main area showing the combined index composite tile with the LUT-colored NDVI render, top-left array name pill, and top-right fps readout. -->

には 2 つのレイアウトが用意されています（上部バーで切り替え可能）：**グリッドビュー**（各タイルが 1 つのセルとなり、 グリッドの鍵アイコンが解除されている場合はドラッグで並べ替え可能）と、**リストビュー**（全幅の行：**統合**アレイは1行（その合成タイル）として表示され、**個別**アレイは**各メンバーに独自の行**が割り当てられ、それぞれ独自のライブフィードとキャリブレーションターゲットテーブルが表示されます； アレイの下には、1台のスタンドアロンカメラ（アクティブなカメラ）が表示されます）。**フィードズーム**スライダーでタイルのサイズを調整できます。セル幅が200ピクセル未満の場合、名前/fpsのオーバーレイは自動的に非表示になります。構成カメラは、サイドバーおよびグリッドのデフォルトレイアウトに、カメラ順 （M3CがM3Mより先、FRGBが最初、モノクロは波長順）で表示されます。グリッドのロックを解除してドラッグすると、グリッドの順序は上書きされます。

<!-- SCREENSHOT-NEEDED: list view of a connected SEPARATE array (1.3.0): one full-width row per member camera, each with its live feed and its own Calibration Target table below it. -->



**個別モード**では、カメラごとに1つのタイルが表示されます。各タイルには以下がオーバーレイ表示されます：

* カメラ名（左上）、
* **fps表示**（右上） — これはバックエンドから報告されるカメラの*実際のキャプチャレート*であり、プレビューのポーリングレートではありません（ライブプレビューはキャプチャレートに関係なく30 fpsに制限されます）、
* ステータスドット — 緑（ストリーミング中）／オレンジ（読み込み中）／赤（エラー）、
* 新しいフレームが2秒間到着しない場合の**古いフレーム表示スピナー** — 接続／切断後、バックエンドがカメラ間で通信帯域を再調整している間、約5秒間はこれが正常な状態です。**複合モード**では、単一の合成タイルが表示されます。バックエンドは、デベイヤー処理、スケーリング、位置合わせ、ノイズ除去を行い、バンドごとの放射輝度（光センサーがバインドされている場合はDLS反射率を含む）に変換し、配列のインデックス式を評価し、 LUTを適用し、結果をMJPEGとしてストリーミングします。最初の位置合わせ済みフレームがレンダリングされるまで、タイルにはその状態が表示されます：「配列の準備中…」、 「位置合わせのキャリブレーション中…」、「最初のフレームを待機中…」、あるいは — タイルの自動位置合わせの再試行（約1分）がタイムアウトした場合 — 「位置合わせが必要」というメッセージと**位置合わせのキャリブレーション**ボタンが表示されます。

アレイタイルのfps表示もストリームの状態を報告します：設定変更（フォーマット、ビニング、ROI）によりカメラが再起動中は**「設定を適用中…」**、アレイは稼働しているもののフレームグループの配信が停止している場合は**「停止中」**、ストリーミングが停止した場合は**「停止中」**と表示されます。この場合はアレイを再接続してください。スペクトルアンミックス処理により、合成画像に表示されるバンドのピクセルの大部分（25％以上）でクリッピングが行われた場合、タイルには**「信頼性の低いバンドデータ・ N%"**と表示されます。そのバンドに基づいて算出されたインデックス値は信頼性が低いと考えられます（通常、1つのバンドで受光量が不足していた場合）。

コンバインドモードに関する有用な情報：

* 合成画像は**マスター**カメラのフレームに位置合わせされています。合成画像に対するAE-ROIの照準合わせやスポット測光は、マスターカメラでは正確ですが、スレーブカメラでは近似値となります。追加のカメラ接続を開かずに、カメラごとのピクセル単位で正確なタイルを表示するには、**Split View**（アレイ設定 → 「メンバーカメラを表示」）を使用してください。
* ****表示レイヤー**（アレイ設定；デフォルトはオフ）を使用すると、前景レイヤーと背景レイヤー（メンバーカメラまたは**インデックス**のいずれか）を選択できます。前景レイヤーを「インデックス」に設定すると、LUTの最小値/最大値の範囲外のピクセルには背景レイヤーが表示されます。
* **レンダリング解像度**（デフォルト 720p）は、ライブストリームの高さ *および* 保存される合成画像のエクスポートサイズを設定します。 カメラごとの画像は常にフル解像度でエクスポートされます。
* アライメントはセッションごとに計算され、保存されることはありません。Chlorosは、メンバーの自動露出が安定した後（最大5分間試行を続けます）、**接続後にすべてのアレイを両方の表示モードで自動的にアライメント調整**します。アレイ設定ペインの**アライメント**セクションには、RMS残差と**アライメントの再キャリブレーション**ボタンが表示されます。これは、合成タイルを持たない個別のアレイについても同様です。

## キャプチャ：モニタリングと分析

アレイのキャプチャ対象は、**モニタリンググレード**（目に見えるものを記録）と**分析グレード**（生データを記録し、後でキャリブレーションを行う）に明確に分類されます：

| ワークフロー | グレード | 保存内容 | GUI | CLI |
| --- | --- | --- | --- | --- |
| **キャプチャ**（静止画） | 分析 | パスごとに1つの同期済みフレームグループ；選択されたすべてのエクスポートレベル（生データ／デベイヤー処理済み／放射輝度／反射率／プレビュー／インデックス）におけるカメラごとのファイル ＋ `.daq` サイドカーファイル |**すべてキャプチャ** ボタン + キャプチャ設定 | `lattice array-capture` |
| **インデックス動画の記録** | モニタリング | 表示されているライブの複合インデックス合成画像 — 8ビット、プレビュー解像度、LUTが焼き込まれています。 GUI ビューを開いていない CLIから、アレイのアライメントが完了すると、バックエンドはアレイの NDVI（または `--expr`）をレンダリングします。フレームが書き込まれない録画は失敗します | ● インデックス動画の記録（複合アレイ） | `lattice array-record` |
| **生データバースト → 動画生成**| 分析 | フルグラブレートでの生センサーフレーム + マニフェスト + `.daq`、その後、DAQの測定値と時間を同期させた、較正済みの放射輝度／反射率／インデックス動画へのオフライン再構成 | ⦿ 生データバーストの記録 →**動画生成** | `lattice array-burst` → `lattice array-build-video` |

経験則：ピクセルデータが*測定値*として利用される場合は、キャプチャまたはバースト（分析グレード）を使用します。アレイが捉えたものを単に*確認またはデモンストレーション*するだけなら、インデックス動画（モニタリンググレード）を記録します。

### キャプチャ設定（GUI）



<!-- SCREENSHOT-NEEDED: Capture Settings pane (gear next to Capture All) with a connected array: capture-mode buttons (Single/Continuous/Interval), the bulk export-type toggle row, the Fastest Capture toggle, and the per-array group card showing the Aligned checkbox and the "Record index video" / "Record raw burst" buttons. -->

**Capture All** の横にある歯車アイコンをクリックすると、キャプチャ設定ペインが開きます（プロジェクトを開いている必要があります — キャプチャデータはそこに保存されます）：

* **キャプチャモード**：**シングル**（1回のみ）／**連続**（連続して実行；キャプチャ回数（デフォルト1）または時間（デフォルト10秒）で制限される）／**インターバル** （タイムラプス：X間隔ごとにN回キャプチャし、合計Y回。デフォルトは5秒ごとに1回、1分間）。
* **カメラごとのエクスポート形式**：Raw、デベイエリング済み、放射輝度、反射率、プレビュー、インデックス — 適用可能なものはすべてデフォルトで有効になっています。RGBフィルター搭載カメラでは、放射輝度/反射率は非表示になります； **反射率は、カメラにDAQ光センサーがある場合のみ表示されます**（カメラ固有のもの、またはアレイから継承されたもの）；インデックスには、設定済みのインデックス式が必要です。
* **アラインメント**（アレイ単位、デフォルトは**オン**）：メンバーのエクスポートデータをアレイのアラインメントプロファイルに合わせてワープし、エクスポートデータがピクセル単位で位置合わせされるようにします。 Rawデータは常にワープ処理されませんが、メタデータに変換情報が含まれます。配列のメンバーファイルは、各カメラのネイティブ方向で保存されます（ミラー反転や回転の設定はファイルに記録されますが、適用はされません）。
* **最速キャプチャ**（トグル）：RAWのみ + 割り当てられたDAQ読み取り値 + フリーの複合インデックス合成。キャプチャ時のキャリブレーション計算をスキップして最大レートを確保します。放射度/反射率/インデックスは、保存された`.daq`から後で再構築します。
* 選択内容はプロジェクトに保持されます。 非表示または一時停止中のカメラはスキップされます。
* アレイでの **連続** モードは、Chlorosバックエンド内で実行されます（1.3.0 での新機能）：リスト内のすべてのカメラがアレイに属している場合、バックエンドがキャプチャループ自体を実行し、1つのグループを書き込みながら次のグループを選択するため、キャプチャごとのリクエストは発生しません。 ドライブが満杯になると実行が停止します（「停止：ドライブ満杯。N件保存、F件失敗」）。 高キャプチャレートに関する Microsoft Defender の注意事項については、[キャプチャ設定とモード](capture.md#capture-modes) を参照してください。

同等の CLI（同じバックエンドエンドポイント、同じ動作）：

```bash
# One synced group, every applicable export level per camera (the default)
chloros-cli lattice array-capture -o output/

# Interval timelapse: one reflectance pass every 10 s for 5 minutes
chloros-cli lattice array-capture --interval 10 --duration 300 --processing reflectance -o timelapse/

# Fastest grab for a moving rig — raw + .daq now, calibrate later
chloros-cli lattice array-capture --fastest -o flightline/

# 30-second monitoring clip of the combined index view, plus a GIF
chloros-cli lattice array-record --duration 30 --fps 10 --gif -o monitoring/

# 5-second analysis-grade raw burst, then build the combined index video
chloros-cli lattice array-burst --duration 5 --build --products combined:index --fps 10 -o capture/
```

キャプチャ用の TIFF圧縮は、`deflate`（ロスレス、デフォルト）または `none` です。完全なフラグテーブル、キャプチャフォルダーのレイアウト、および再処理ルールについては、 [CLIリファレンス](../reference/cli-reference.md#capture-modes-recorders--offline-reprocess)に記載されています。

## DAQ光センサーのペアリング

反射率および照度補正済みのプレビューを表示するには、DAQセンサー（**Light Sensors**タブで接続済み）からの下向き光データが必要です：

* サイドバーの**アレイ行**には、**「DAQ · オン/オフ」ピル**が表示されます。アレイレベルの光センサーが設定されている場合、**または**構成カメラのいずれかに独自のセンサーが設定されている場合は*オン*になります。そのツールチップには、どのセンサーがどのカメラにデータを送信しているかが正確に表示されます。
* アレイ設定 → **周囲光センサー**→**光センサー** ドロップダウンから、アレイ全体に割り当てます。この設定はプロジェクトに保存され、すべての構成カメラに反映されますが、個々のカメラは独自のセンサーでこの設定を上書きすることも可能です。
* その下のステータス行には、現在の状態が表示されます： **オフ**→ 「最初のスペクトルを待機中…」 →**「アクティブ — アレイ内のすべてのカメラで照度補正が適用されています」** → または、過去 3 秒間に新しいスペクトルが到着しなかった場合は、古いデータである旨の通知が表示されます。この場合、最後の測定値が引き続き使用されます（キャプチャパス上では測定値の有効期限は切れません）。

センサーが割り当てられている場合：「反射率」エクスポートタイプが利用可能になり、ライブプレビューは照度補正され、予測自動露出がスペクトルを利用できるようになり、すべての反射率キャプチャでは、実際に使用されたDAQ測定値が**`.daq`ファイル**としてキャプチャの `daq/`フォルダに書き込まれ、後でキャプチャを再処理できるようになります。その隣には、その測定値がどのカメラのフレームを表すかを示す `.daq.cameras.json` ファイルがあります。再処理の際、Chlorosはその測定値をそれらのカメラからの画像にのみ照合します。
