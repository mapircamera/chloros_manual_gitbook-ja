# ダイナミック・コンピュート・アダプテーション

Chloros 1.2.0 は、ハードウェア検出機能と自動処理戦略選択機能を備えています。処理エンジンは、Jetson Orin Nano からマルチ GPU ワークステーションに至るまで、手動での設定を一切必要とせずに、お使いのハードウェアに合わせて適応します。

***

## 仕組み

Chlorosの起動時、システムのプロファイリングが行われます：

1. **オペレーティングシステムの検出** — Windows または Linux
2. **CPU コア数および総 RAM 容量の特定**

3.**GPU の有無の検出** — NVIDIA CUDA 機能、VRAM、モデル
4. **Jetson モデルの識別**（該当する場合） — `/proc/device-tree/model` 経由
5. **温度センサーの確認**（Jetson） — 温度を考慮した処理のため
6. **演算戦略の選択** — 検出されたすべてのハードウェアに基づいて
7. **ワーカー数、パイプラインタイプ、およびメモリ割り当ての自動設定**

検出されたプロファイルは、セッション用にメモリとディスクにキャッシュされるため、以降の実行はより高速に開始されます：

| プラットフォーム | キャッシュされたプロファイル |
| --- | --- |
| **Linux / Jetson** | `~/.config/chloros/system_config.json` (`XDG_CONFIG_HOME`を優先) |
| **Windows** | `%LOCALAPPDATA%\Chloros\config\system_config.json` |

そのファイルを削除すると、再検出が強制されます。これは、GPUやRAMを追加した後に役立ちます。また、互換性のない古いバージョンによってキャッシュが書き込まれた場合、Chlorosも自動的に再検出を行います。

***

## 演算戦略

Chlorosは、お使いのハードウェアに基づいて3つの演算戦略のうち1つを選択します：

| 戦略 | 選択条件 | ワーカー | 実行者 | パイプライン |
| --- | --- | --- | --- | --- |
| **`GPU_PARALLEL`**|**12GB以上のVRAM**を報告するCUDA GPU（Jetsonの統合メモリの場合、合計12GB以上の共有RAMも必要） | `min(4, VRAM ÷ 4GB)`、最低2 —**Jetsonでは最大2まで** | `ProcessPoolExecutor` (spawn) | `fused_gpu` |
| **`GPU_SINGLE`**|**2～12GBのVRAM**を搭載したCUDA GPU | 3（I/Oオーバーラップ； セマフォによる GPU アクセスのシリアル化）。**RAM が 12GB 未満の Jetson では 1（順次）** | `ProcessPoolExecutor` (spawn); RAM容量の少ないJetsonではプロセス内順次実行 | `fused_gpu` / `tiled_gpu` |
| **`CPU_PARALLEL`** | CUDA GPUなし、またはVRAMが2GB未満 | `max(2, physical cores − 1)` | `ThreadPoolExecutor` | `cpu_fallback` |

`GPU_PARALLEL`ワーカー算出式の具体例：VRAM 12GB → 3ワーカー、16GB以上 → 4ワーカー、Jetsonならどれでも → 2ワーカー。

並列処理は、Pythonの標準的な`concurrent.futures`を用いて実装されています。GPU戦略では、**spawn**開始メソッドを持つ`ProcessPoolExecutor`を使用します （各ワーカーは独自の CUDA コンテキストを持つ独立したプロセスであり、`fork` を使用すると、すでに初期化された CUDA 状態がコピーされ、子プロセスが破損してしまうため）を使用し、CPU 戦略では `ThreadPoolExecutor` を使用します。 Chlorosは、Rayなどのサードパーティ製の分散フレームワークを一切使用しません。

### パイプラインの種類

* **`fused_gpu`** — 完全な GPU 処理パス。デベイヤー処理、補正、およびインデックス演算が、1 回の融合パスで GPU 上で実行されます。スループットが最も高く、VRAM を最も多く必要とします。
* **`tiled_gpu`** — メモリ効率に優れた GPU パス。限られた GPU メモリ内に収まるよう、画像をタイル単位で処理します。スループットは低くなりますが、メモリに制約のあるデバイスでも動作します。
* **`cpu_fallback`** — マルチスレッド並列処理を用いたCPUのみの処理。NVIDIA GPUが利用できない場合や、両方のGPUパスが失敗した際の最終手段としてのフォールバックとして使用される。

ランタイムのフォールバックチェーンは、常に `fused_gpu` → `tiled_gpu` → `cpu_fallback` の順になります。

***

## 戦略の手動上書き

特定の戦略を強制的に適用するには、`CHLOROS_STRATEGY` 環境変数を設定します。これは、自動検出の結果が状況に適さないもの（例えば、GPUを他の作業のために空けておきたい場合など）を選択してしまった際の、専門家向けの緊急回避策です：

```bash
# Valid values: CPU_PARALLEL, GPU_SINGLE, GPU_PARALLEL
CHLOROS_STRATEGY=CPU_PARALLEL chloros-cli process ~/datasets/flight001
```

この変数の照合は大文字小文字を区別しません。3つの名前以外のものはすべて無視され、自動検出は通常通り行われます。オーバーライドが設定されている場合でも、Chlorosは引き続きワーカー数を自動的に選択します：

| オーバーライド | 使用されるワーカー数 |
| --- | --- |
| `CPU_PARALLEL` | `max(2, physical cores − 1)` |
| `GPU_SINGLE` | 3 |
| `GPU_PARALLEL` | `min(4, physical cores)` |

恒久的な設定ではなく、コマンドごとに設定することを推奨します。そうすることで、通常の実行では自動適応が維持されます。

## プラットフォーム固有の挙動

| プラットフォーム | 戦略 | ワーカー | パイプライン | 備考 |
| --- | --- | --- | --- | --- |
| **Jetson Orin Nano 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (順次処理) | メモリ効率の高いモード、1 イメージずつ |
| **Jetson Orin NX 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (順次) | 共有RAMが12GB未満のため、順次処理が強制される |
| **Jetson Orin NX 16GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (並列) | 推奨エッジデバイス — Jetsonではワーカー数が2に制限 |
| **Jetson AGX Orin 32-64GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (並行) | 最高のエッジパフォーマンス（Jetson側でワーカー数2に制限） |
| **8GB GPU搭載デスクトップ** | `GPU_SINGLE` | 3 | `fused_gpu` / `tiled_gpu` | 3ワーカーがI/Oを並行処理し、セマフォがGPUアクセスをシリアル化する |
| **12GB以上のGPUを搭載したデスクトップ** | `GPU_PARALLEL` | 3-4 | `fused_gpu`（並行） | デスクトップでの最適パフォーマンス：12GB → 3ワーカー、16GB以上 → 4 |
| **CPUのみのシステム** | `CPU_PARALLEL` | 物理コア数 − 1（最低2） | `cpu_fallback` | GPU不要、スレッドプールを使用 |

{% hint style="info" %}
**Jetson 統合メモリ**：Jetson デバイスは GPU と CPU のメモリを共有します。Jetson Orin NX 16GB では約 15.3GB の VRAM が報告されますが、これは OS や CPU プロセスで使用される物理 RAM と同じものです。 そのため、16GB以上のJetsonは、12GB以上のデスクトップGPUと同様に`GPU_PARALLEL`の対象となりますが、ワーカー数は2つに制限されます。GPU、ワーカープロセス、およびワーカーごとのCUDAコンテキストはすべて、同じ共有プールから割り当てを受けるためです。
{% endhint %}

### VRAM による GPU バジェット（ディスクリート GPU）

NVIDIAのディスクリートGPUを搭載したx86_64ホストでは、検出されたVRAMの容量によって、カード処理が割り当てられるリソース量やバッチサイズの最大値も決定されます：

| 検出されたVRAM | GPUバジェットの上限 | バッチサイズ乗数 |
| --- | --- | --- |
| **8GB以上** | 90% | ×2.0 |
| **6～8GB** | 85% | ×1.75 |
| **

3.5～6GB** | 80% | ×1.5 |
| **2～3.5GB** | 75% | ×1.25 |
| **2GB未満** | 70% | ×1.0 |

ディスクリート GPU はシステム RAM を共有しないため、システム用に確保されるメモリは 0.5GB のみです。 Jetsonプロファイルでは、はるかに多くのメモリが確保され、上限も低くなっています。詳細は[NVIDIA Jetsonガイド](../linux/nvidia-jetson-guide.md#per-model-gpu-budget)を参照してください。

## 動的なGPUメモリ割り当て

Chlorosは、[4スレッド処理パイプライン](processing-pipeline.md)を採用しています：

* **スレッド1**（検出） — 画像の読み込み、EXIFデータの解析、ターゲットの検出
* **スレッド 2**（キャリブレーション） — 反射率キャリブレーションの計算
* **スレッド 3**（処理） — GPU デベイヤー、ヴィネット補正、インデックス計算
* **スレッド 4**（エクスポート） — ファイル書き込み、メタデータ埋め込み

スレッド 1、2、4 は GPU 負荷が軽く、スレッド 3 が負荷が高いです。前のパイプラインスレッドが終了すると、その GPU リソースは **残りのアクティブなスレッドに再配分** されるため、実行が進むにつれてスレッド 3 が徐々に多くのメモリを確保できるようになります。

### 割り当て段階

| 段階 | アクティブなスレッド | GPUメモリの配分 |
| --- | --- | --- |
| **初期** | 1、2、3、4 | すべてのスレッドに分散、その大部分はスレッド3へ |
| **初期中期** | 2, 3, 4 | スレッド1の割り当て分が再配分 |
| **中期後期** | 3, 4 | スレッド1および2の割り当て分が3および4に |
| **後期** | 3 または 4 | 最後にアクティブになったスレッドが、そのプロファイルの最大割り当て量を受け取る |

数値の決定には以下の2つのルールが適用されます：

* **唯一**のアクティブスレッドには、そのプロファイルの最大割り当て量が割り当てられます。
* 複数の *負荷の高い* GPU タスクがアクティブな場合、各負荷の高いタスクの基本割り当てはそれら間で分割されます（設定された最小値を下回ることはありません）。

実行時に実際に使用される値は、プラットフォームプロファイルの割り当てとGPUメモリモニターからのリアルタイム推奨値の**低い**方となるため、負荷の高いカードは、楽観的なプロファイル設定よりも常に優先されます。***

## テクスチャ対応処理

テクスチャ対応デベイヤー（**Chloros+ のみ** — `--debayer texture-aware`）は、コピーごとに約1.75GBのFP16 VRAMを必要とするAI/MLノイズ除去モデルを実行するため、標準方式よりもはるかに多くのGPUメモリを使用します：

* **7GB未満のVRAM**を搭載したシステムでは、テクスチャ対応処理を**同期ループで1画像ずつ**処理します。複数のモデルコピーを同時に実行する余裕がなく、ワーカープールを設定しても競合が生じるだけだからです
* **7GB以上のVRAM**を搭載したシステムでは、**Standard**と比較してワーカー数は減少しますが、Texture Awareを並列処理できます
* **Jetson**では、 Texture Awareは常に単一のワーカーに固定され、低消費電力モデル（Nano、Orin Nano）ではGPU周波数の上限も自動的に適用されます — [NVIDIA Jetsonガイド](../linux/nvidia-jetson-guide.md#gpu-frequency-cap-for-texture-aware-on-nano-and-orin-nano)を参照してください***

## 熱管理（Jetson）

Jetsonデバイスには、特に密閉環境や航空機搭載環境において、熱的な制約があります。Chlorosは、Jetsonのオンボード温度センサーを監視し、バッチサイズを自動的に調整します：

| 温度 | 対応 |
| --- | --- |
| **&lt; 70°C** | 通常動作 — フルスピード |
| **70°C** (警告) | バッチサイズが段階的に縮小されます（70°C～80°Cの範囲で100% → 50%） |
| **80°C** (危険) | 大幅なスロットリング（80°C～90°Cの間で50% → 0%） |
| **90°C** (シャットダウン) | GPU処理を完全に停止 |

十分な冷却機能を備えたデスクトップシステムでは、サーマルスロットリングが作動することはほとんどありません。

***

## メモリ負荷への対応

Chlorosは、処理中にGPUメモリを継続的に監視し、3つのレベルで対応します。

**バッチサイズの調整。** バッチは、8枚の画像に上記の表にあるプラットフォーム係数を掛けた数から始まります。その後、Chlorosは空きVRAMを確認し、 その20％をPyTorch自身のオーバーヘッド用に確保し、12MPの画像あたり約100MBのGPUメモリを想定します。バッチサイズは、メモリから算出された上限とプラットフォームの基準値のうち、小さい方の値となります。バッチサイズは1を下回ることはありません。**予防的な縮小。** **VRAM使用率が85%**を超えると、何らかの障害が発生する前にバッチサイズが縮小されます。**スレッドごとの割り当て調整。** リアルタイムの使用率が上昇するにつれて、各スレッドのGPU割り当て量は縮小されます：使用率80%超で×0.75、90%超で×0.5となります。 モニターの閾値は、70%（保守的）、85%（通常動作限界）、95%（OOMリスク）です。**OOM時のバックオフと回復。** 万が一、メモリ不足（OOM）が発生した場合：

* バッチサイズは**半減**され、OOMが連続して発生するたびにさらに半減されます。その後、バッチが正常に実行されるたびに、このペナルティは1段階ずつ緩和されます
* アクティブなスレッドの割り当ては現在の値の70%に削減され、アロケータは保守的な戦略に切り替わります。割り当てが連続して成功すると、再び緩和されます
* 深刻な負荷下では、パイプラインは`fused_gpu`から`tiled_gpu`へ、そして最終手段として`cpu_fallback`へとフォールバックします

**ホスト RAM (Jetson)。** 処理開始前に、CLI は画像数とデベイヤーモードからホストメモリのピーク値を推定し、RAM とファイルベースのスワップ領域を合わせても不足する可能性がある場合は警告を表示します。その際、スワップ領域を追加するための正確なコマンドを出力します — 詳細は [NVIDIA Jetson ガイド](../linux/nvidia-jetson-guide.md#swap-warning-and-recommendations)を参照してください。***

## 演算適応の監視

### システム診断

`chloros-cli selftest`は、演算レイヤーが認識している情報を確認する最も迅速な方法です：

```bash
chloros-cli selftest
```

このコマンドの7つのチェック項目は、バージョン、ポートの可用性、バックエンドの起動、`/api/test`、システム情報、ノイズ除去モデルの有無、およびCUDAとノイズ除去モデルの準備状況です。チェック5では、ハードウェア情報を直接表示します：

```
      GPU: NVIDIA RTX A4000, CUDA: True, PyTorch: 2.7.0
```

チェック7は`CUDA: <bool>, Denoiser: <bool>`を出力します。Texture Awareを一切使用可能にするには、この2つがともにtrueである必要があります。

### バックエンドログ

戦略とワーカー数は、各実行の開始時にバックエンド内部で決定されます。これらを通知する CLI バナーは存在しません。 予期しない動作（GPUパスのフォールバック、OOM、ノイズ除去モジュールの読み込み失敗など）が発生した場合、そのセッションのバックエンドログにその情報が記録されます：

| プラットフォーム | ログの場所 |
| --- | --- |
| **Linux / Jetson** | `~/.cache/chloros/logs/backend_<YYYYMMDD_HHMMSS>.log`（起動ごとに1ファイル） |
| **Linux、CLI-started backend** | 同じく `~/.chloros/backend.log` |
| **Windows** | `%LOCALAPPDATA%\Chloros\logs\` |

### リアルタイムの進捗状況

実行中、CLIは、サーバー送信イベント（Server-Sent Events）を介してストリーミングされるスレッドごとのリアルタイム進捗状況（検出、分析、処理、エクスポート）を表示します。これは、スレッド3がボトルネックであるかどうかを判断するための実用的な指標となります。 [処理パイプライン](processing-pipeline.md)を参照してください。
