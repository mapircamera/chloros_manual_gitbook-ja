# ダイナミック・コンピュート・アダプテーション

Chloros
1.3.0は、ハードウェア検出と処理戦略の自動選択機能を備えています。処理エンジンは、Jetson Orin NanoからマルチGPUワークステーションに至るまで、手動での設定を一切必要とせずに、お使いのハードウェアに適応します。

***

## 仕組み

Chloros
の起動時、システムのプロファイリングが行われます：

1. **オペレーティングシステムの検出** — Windows
または Linux
2. **CPUコア数と総RAM容量の特定**

3.**GPUの有無の検出** — NVIDIA CUDA機能、VRAM、モデル
4. **Jetsonモデルの特定**（該当する場合） — `/proc/device-tree/model`を介して
5. **温度センサーの確認**（Jetson） — 温度を考慮した処理のため
6. **演算戦略の選択** — 検出されたすべてのハードウェアに基づいて
7. **ワーカー数、パイプラインタイプ、およびメモリ割り当てを**自動的に設定

検出されたプロファイルは、セッション中にメモリとディスクにキャッシュされるため、以降の実行はより高速に開始されます：

| プラットフォーム | キャッシュされたプロファイル |
| --- | --- |
| **Linux
/ Jetson** | `~/.config/chloros/system_config.json` (`XDG_CONFIG_HOME` を優先) |
| **Windows** | `%LOCALAPPDATA%\Chloros\config\system_config.json` |

そのファイルを削除すると、再検出が強制されます。これは、GPU や RAM を追加した後に役立ちます。また、互換性のない古いバージョンによってキャッシュが書き込まれた場合、Chloros
は自動的に再検出を行います。

***

## 演算戦略

Chloros
は、お使いのハードウェアに基づいて、3 つの演算戦略のうち 1 つを選択します：

| 戦略 | 選択条件 | ワーカー数 | 実行者 | パイプライン |
| --- | --- | --- | --- | --- |
| **`GPU_PARALLEL`**|**12GB以上のVRAM**を報告するCUDA GPU （Jetsonのユニファイドメモリの場合、合計12GB以上の共有RAMも必要） | `min(4, ⌊(VRAM − 0.5GB) × 0.9 ÷ 3.5GB⌋)`、最低2 —**Jetsonでは2に制限** | ワーカープロセス（個別のCUDAコンテキスト） | `fused_gpu` |
| **`GPU_SINGLE`**|**2～12GBのVRAM**を搭載したCUDA GPU | 3（I/Oオーバーラップ；セマフォによるGPUアクセスのシリアル化）。**RAMが12GB未満のJetsonでは1（順次）** | ワーカープロセス（個別のCUDAコンテキスト）；RAM容量の少ないJetsonではプロセス内順次実行 | `fused_gpu` / `tiled_gpu` |
| **`CPU_PARALLEL`** | CUDA GPUなし、またはVRAMが2GB未満 | `max(2, physical cores − 1)` | `ThreadPoolExecutor` | `cpu_fallback` |

`GPU_PARALLEL` ワーカー算出式の具体例：VRAM 12GB → 2 ワーカー、16GB → 3 ワーカー、20GB以上 → 4 ワーカー。 各ワーカーには、0.5GBの予備を確保した後の残りのVRAMの90%の範囲内で、Texture Awareタスクの測定された必要量である3.5GBが割り当てられます。

{% hint style="info" %}
**GPU戦略では、CUDAを使用できるPyTorchが必要です。** PyTorchで利用可能なCUDAデバイスがないマシンは、GPUの種類にかかわらず`CPU_PARALLEL`が割り当てられます。 1.3.0 版の Jetson パッケージは JetPack 6 の CUDA ビルド版 PyTorch を使用しているため、JetPack の CUDA および cuDNN ライブラリがインストールされていれば、Jetson は要件を満たします。RAM が 12GB 未満の Jetson は、常に 1 枚の画像を一度に、プロセス内で処理します （`GPU_SINGLE`としてログに記録されます）。
{% endhint %}

GPU戦略では、ワーカープロセスのプールが実行されます。各ワーカープロセスは個別のOSプロセスであり、独自のCUDAコンテキストを持っています。Chloros
は、パッケージ内のアプリケーション内ではワーカーの起動が機能しないPython
の`multiprocessing`を経由せず、独自にインストールされたバックエンドプログラムを再度起動することで、これらのワーカープロセスを開始します。 CPU 戦略ではスレッドプール（Python
の `ThreadPoolExecutor`）を使用します。Chloros
は、Ray などのサードパーティ製の分散フレームワークを一切使用しません。

### パイプラインの種類

* **`fused_gpu`** — 完全なGPU処理パス。デベイヤー処理、補正、およびインデックス演算が、単一の融合パスでGPU上で実行されます。スループットが最も高く、VRAMを最も多く必要とします。
* **`tiled_gpu`** — メモリ効率に優れたGPUパス。限られたGPUメモリ内に収まるよう、画像をタイル単位で処理します。スループットは低くなりますが、メモリに制約のあるデバイスでも動作します。
* **`cpu_fallback`** — マルチスレッド並列処理を用いたCPUのみの処理。NVIDIA GPUが利用できない場合、および両方のGPUパスが失敗した際の最終手段としてのフォールバックとして使用されます。

ランタイムのフォールバックチェーンは、常に `fused_gpu` → `tiled_gpu` → `cpu_fallback` の順になります。

***

## 戦略の手動上書き

特定の戦略を強制的に適用するには、環境変数 `CHLOROS_STRATEGY` を設定します。これは、自動検出が状況に適さない戦略を選択した場合（例えば、他の作業のために GPU を空けておきたい場合など）のための、専門家向けの緊急回避策です：

```bash
# Valid values: CPU_PARALLEL, GPU_SINGLE, GPU_PARALLEL
CHLOROS_STRATEGY=CPU_PARALLEL chloros-cli process ~/datasets/flight001
```

この変数の照合は大文字小文字を区別しません。3つの名称のいずれにも該当しないものは無視され、自動検出は通常通り行われます。オーバーライドが設定されている場合でも、Chloros
は引き続きワーカー数を自動的に決定します：

| オーバーライド | 使用されるワーカー数 |
| --- | --- |
| `CPU_PARALLEL` | `max(2, physical cores − 1)` |
| `GPU_SINGLE` | 3 |
| `GPU_PARALLEL` | `min(4, physical cores)` |

使用可能な CUDA デバイスがないマシンで `GPU_SINGLE` または `GPU_PARALLEL` のオーバーライドを試みると、ログに `[STRATEGY]` という行が記録され、 実行時には `CPU_PARALLEL` が使用されます。

恒久的な設定ではなく、コマンドごとに設定することを推奨します。そうすることで、通常の実行では自動適応が維持されます。

## プラットフォーム固有の挙動

| プラットフォーム | 戦略 | ワーカー | パイプライン | 備考 |
| --- | --- | --- | --- | --- |
| **Jetson Orin Nano 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (順次) | メモリ効率の高いモード、1回につき1つのイメージ |
| **Jetson Orin NX 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (順次) | 共有RAMが12GB未満のため、順次処理が強制される |
| **Jetson Orin NX 16GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (並列) | 推奨エッジデバイス — Jetsonではワーカー数が2つに制限 |
| **Jetson AGX Orin 32～64GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (並行) | 最高のエッジパフォーマンス（Jetson側でワーカー数2に制限） |
| **8GB GPU搭載デスクトップ** | `GPU_SINGLE` | 3 | `fused_gpu` / `tiled_gpu` | 3 ワーカーが I/O をオーバーラップさせ、セマフォが GPU アクセスをシリアル化 |
| **12GB以上のGPUを搭載したデスクトップ** | `GPU_PARALLEL` | 2～4 | `fused_gpu` (並列) | デスクトップの最適パフォーマンス：12GB → 2ワーカー、16GB → 3、20GB以上 → 4 |
| **CPUのみのシステム** | `CPU_PARALLEL` | 物理コア数 − 1（最小2） | `cpu_fallback` | GPU不要、スレッドプールを使用 |

{% hint style="info" %}
**Jetsonの統合メモリ**：JetsonデバイスはGPUとCPUのメモリを共有します。Jetson Orin NX 16GBでは約15.3GBのVRAMが報告されますが、これはOSやCPUプロセスで使用される物理RAMと同じものです。 そのため、16GB以上のJetsonデバイスは、12GB以上のデスクトップGPUと同様に`GPU_PARALLEL`の対象となりますが、ワーカー数は2つに制限されます。GPU、ワーカープロセス、および各ワーカーのCUDAコンテキストはすべて、同じ共有プールから割り当てを受けるためです。
{% endhint %}

### VRAM に基づく GPU バジェット（ディスクリート GPU）

NVIDIA ディスクリート GPU を搭載した x86_64 ホストでは、検出された VRAM の容量によって、カードが処理に割り当てられるリソース量やバッチサイズの最大値が決まります：

| 検出されたVRAM | GPUバジェットの上限 | バッチサイズの乗数 |
| --- | --- | --- |
| **8GB以上** | 90% | ×2.0 |
| **6～8GB** | 85% | ×1.75 |
| **

3.5～6GB** | 80% | ×1.5 |
| **2～3.5GB** | 75% | ×1.25 |
| **2GB未満** | 70% | ×1.0 |

ディスクリートGPUはシステムRAMを共有しないため、システム用に確保するメモリは0.5GBのみです。Jetsonプロファイルでは、はるかに多くのメモリを確保し、上限も低く設定されています。詳細は[NVIDIA Jetsonガイド](../linux/nvidia-jetson-guide.md#per-model-gpu-budget)を参照してください。

## 動的なGPUメモリ割り当て

Chloros
は[4スレッドの処理パイプライン](processing-pipeline.md)を採用しています：

* **スレッド1**（検出） — 画像の読み込み、EXIFの解析、ターゲットの検出
* **スレッド2**（キャリブレーション） — 反射率キャリブレーションの計算
* **スレッド 3** (処理) — GPU デベイヤー、ヴィネット補正、インデックス計算
* **スレッド 4** (エクスポート) — ファイル書き込み、メタデータの埋め込み

スレッド 1、2、4 は GPU 負荷が軽いです。 スレッド3が最も負荷が高い。先行するパイプラインのスレッドが処理を完了すると、そのGPUリソースは**残りのアクティブなスレッドに再配分**されるため、実行が進むにつれてスレッド3に割り当てられるメモリは徐々に増加する。

### 割り当て段階

| 段階 | アクティブなスレッド | GPUメモリの配分 |
| --- | --- | --- |
| **初期** | 1, 2, 3, 4 | すべてのスレッドに分散、その大部分はスレッド3に割り当て |
| **初期～中期** | 2, 3, 4 | スレッド1の割り当て分が再配分 |
| **中期～後期** | 3, 4 | スレッド1および2の割り当て分が3および4に割り当てられる |
| **後期** | 3 または 4 | 最後にアクティブになったスレッドが、そのプロファイルの最大割り当て量を受け取る |

数値の決定には以下の2つのルールが適用されます：

* **唯一**アクティブなスレッドには、そのプロファイルの最大割り当て量が与えられます。
* 複数の「負荷の高い」GPUタスクがアクティブな場合、各負荷の高いタスクの基本割り当て量はそれらに分配されます（設定された最小値を下回ることはありません）。

実行時に実際に使用される値は、プラットフォームプロファイルの割り当て量とGPUメモリモニターからのリアルタイム推奨値の**どちらか低い方**となるため、負荷の高いGPUカードは、楽観的なプロファイル設定よりも常に優先されます。***

## テクスチャ対応処理

Texture Aware デベイヤー（**Chloros
+ のみ** — `--debayer texture-aware`）は、コピーごとに約 1.75GB の FP16 VRAM を必要とする AI/ML ノイズ除去モデルを実行するため、標準的な方法よりもはるかに多くの GPU メモリを使用します：

* **7GB未満のVRAM**を搭載したシステムでは、テクスチャ対応処理を**同期ループで1画像ずつ**処理します。複数のモデルコピーを同時に処理する余裕がなく、ワーカープールを増やしても競合が生じるだけだからです
* **7GB以上のVRAM**を搭載したシステムでは、Texture Awareを並列処理できますが、Standardと比較してワーカー数は減少します
* **Jetson** では、Texture Aware は常に単一のワーカーに固定されます
* **使用可能な CUDA GPU がない**場合、実行では標準のデベイヤーが使用され、バックエンドにはその理由を説明する「`[DEBAYER] … needs a CUDA GPU …`」という行が1行ログに記録されます
* 低消費電力のJetson（Nano、Orin Nano）では、CLI
でTexture Awareを要求するとGPUの周波数上限が適用されます — [NVIDIA Jetsonガイド](../linux/nvidia-jetson-guide.md#gpu-frequency-cap-for-texture-aware-on-nano-and-orin-nano)を参照してください

## 熱管理 (Jetson)

Jetson デバイスには、特に密閉環境や航空機搭載環境において、熱的な制約があります。Chloros
は Jetson のオンボード温度センサーを監視し、バッチサイズを自動的に調整します：

| 温度 | 対応 |
| --- | --- |
| **&lt; 70°C** | 通常動作 — フルスピード |
| **70°C** (警告) | バッチサイズを段階的に縮小 (70°C から 80°C の間で 100% → 50%) |
| **80°C** (危険) | 大幅なスロットリング (80°C～90°Cの間で50% → 0%) |
| **90°C** (シャットダウン) | GPU処理を完全に停止 |

十分な冷却機能を備えたデスクトップシステムでは、サーマルスロットリングが作動することはほとんどありません。

***

## メモリ圧力の処理

Chloros
は処理中にGPUメモリを継続的に監視し、3つのレベルで対応します。

**バッチサイズの調整。** バッチは、8枚の画像に上記の表にあるプラットフォーム係数を掛けた数から始まります。Chloros
はその後、空きVRAMを確認し、その20％をPyTorch自身のオーバーヘッド用に確保し、12MPの画像1枚あたり約100MBのGPUメモリを想定します。バッチサイズは、メモリに基づく上限とプラットフォームの基準値のうち、小さい方の値となります。 バッチサイズは1を下回ることはありません。

**予防的な縮小。** **VRAM使用率が85%**を超えると、何らかの障害が発生する前にバッチサイズが縮小されます。**スレッドごとの割り当て削減。** リアルタイム使用率が上昇するにつれて、各スレッドのGPU割り当ては縮小されます：使用率80%を超えると×0.75、90%を超えると×0.5となります。 モニターの閾値は、70%（保守的）、85%（通常動作限界）、95%（OOMリスク）です。**OOM時のバックオフと回復。** それでもメモリ不足（OOM）イベントが発生した場合：

* バッチサイズは**半減**され、OOMが連続して発生するたびにさらに半減されます。その後、バッチが正常に実行されるたびに、このペナルティは1段階ずつ緩和されます
* アクティブなスレッドの割り当ては現在の値の70%に削減され、アロケータは保守的な戦略に切り替わります。割り当てが連続して成功すると、再び緩和されます
* 深刻な負荷下では、パイプラインは `fused_gpu` から `tiled_gpu` へ、そして最終手段として `cpu_fallback` へと切り替わります

**ホスト RAM（Jetson）。** 処理の前に、CLI
は画像数とデベイヤーモードからホストメモリのピーク値を推定し、RAMとファイルベースのスワップ領域の合計が不足する可能性がある場合は警告を表示します。その際、スワップ領域を追加するための正確なコマンドも出力されます。詳細は[NVIDIA Jetsonガイド](../linux/nvidia-jetson-guide.md#swap-warning-and-recommendations)を参照してください。

## 演算適応の監視

### システム診断

`chloros-cli selftest` は、演算レイヤーが認識している情報を確認する最も迅速な方法です：

```bash
chloros-cli selftest
```

その 7 つのチェック項目は、バージョン、ポートの可用性、バックエンドの起動、`/api/test`、システム情報、ノイズ除去モデルの有無、および CUDA とノイズ除去モデルの準備状況です。チェック 5 では、ハードウェア行が直接出力されます：

```
      GPU: NVIDIA RTX A4000, CUDA: True, PyTorch: 2.7.0
```

チェック7では`CUDA: <bool>, Denoiser: <bool>`が出力されます。Texture Awareを一切使用可能にするには、この両方が真でなければなりません。

### バックエンドのログ

戦略とワーカー数は、各実行の開始時にバックエンド内部で決定されます。これらを通知するCLI
バナーは存在しません。予期しない動作（GPUパスのフォールバック、OOM、ノイズ除去モデルの読み込み失敗など）が発生した場合、そのセッションのバックエンドログにその情報が記録されます：

| プラットフォーム | ログの保存場所 |
| --- | --- |
| **Linux
/ Jetson** | `~/.cache/chloros/logs/backend_<YYYYMMDD_HHMMSS>.log`（起動ごとに1ファイル） |
| **Linux
、CLI
から起動されたバックエンド** | 同様に `~/.chloros/backend.log` |
| **Windows** | `%LOCALAPPDATA%\Chloros\logs\` |

### リアルタイムの進捗状況

実行中、CLI
には、Server-Sent Eventsを介してストリーミングされるスレッドごとのリアルタイム進捗状況（検出、分析、処理、エクスポート）が表示されます。これは、スレッド3がボトルネックになっているかどうかを判断するための実用的な指標となります。[処理パイプライン](processing-pipeline.md)を参照してください。
