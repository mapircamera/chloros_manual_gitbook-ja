# 処理パイプライン

Chloros 1.3.0 では、段階的な組立ラインのように機能する 4 スレッドの処理パイプラインを採用しています。各スレッドがワークフローの異なるフェーズを処理するため、複数の画像が同時に異なる段階で処理されることが可能です。

***

## パイプラインのアーキテクチャ

```

Images In → [Thread 1: Detection] → [Thread 2: Calibration] → [Thread 3: Processing] → [Thread 4: Export] → Files Out
```

すべての画像は、4つのスレッドすべてを順番に通過します。Chloros+のマルチスレッド処理では、複数の画像が同時に異なるスレッドで処理されます。つまり、スレッド3が1つの画像を処理している間、スレッド1は次の画像の検出を行い、スレッド2は別の画像のキャリブレーションを行い、スレッド4は処理完了した画像をディスクに書き込むといったことが可能です。

進行状況はスレッドごとに報告され、Server-Sent Events を通じてストリーミングされます（バックエンドは `/api/events` 上でこれらを公開します）。CLI のリアルタイム進行状況表示では、4つの段階が **検出、分析、処理、エクスポート** と表示されます。***

## スレッドの詳細

### スレッド 1: 検出

**目的**: 画像を読み込み、キャリブレーションターゲットを検出します。

* ディスクから画像ファイルを読み込みます — Survey3の`.raw`+`.jpg`ペア、 LATTICE `.tif`/`.tiff` キャプチャ、および `.dng`
* EXIF メタデータ（GPS、カメラモデル、タイムスタンプ、露出）を抽出
* キャリブレーションターゲットを検出：LATTICEのキャプチャ画像についてはArUcoマーク付きターゲット形状、Survey3のキャリブレーションターゲット写真については従来のパネル検出器
* 出力：画像データ + メタデータ + ターゲット検出結果

主にI/OおよびCPUに依存するスレッド。

### スレッド 2：キャリブレーション

**目的**：検出されたターゲットからキャリブレーションパラメータを算出する。

* ターゲット画像から反射率キャリブレーション係数を算出
* ヴィネット補正パラメータを算出
* バンドごとのキャリブレーションカーブを決定
* 出力：各画像のキャリブレーションパラメータ

CPUに依存する計算スレッドです。Survey3または混合実行の場合、反射率キャリブレーションが有効になっているとスレッド3はこのスレッドを待機するため、画像の処理が始まる前に係数が準備されます。LATTICEのみの実行では、スレッド3は検出中に実行されます。各フレームは、そのターゲットのアンカーが確定してから開始されます。 1フレームは、時間的に最も近いターゲットを前後どちらからでも取得するため、現在の最も近いターゲットよりも時間的に近いカメラのすべてのフレームがスキャンされるまで待機します。生成される成果物は同じですが、より早く得られます。

### スレッド3：処理（GPU）

**目的**：補正を適用し、植生指数を算出する。**これは最も計算負荷の高いスレッドである。*** **デベイヤー処理**：RAWベイヤーデータをマルチチャンネル画像に変換する
  * 標準（高速、中品質） — デフォルト、`--debayer standard`
  * テクスチャ対応（低速、最高品質） — Chloros+ 専用、`--debayer texture-aware`、AI/ML ノイズ除去モデルを使用
  * LATTICEモノクロ（M3M）のキャプチャはシングルバンドであるため、デモザイクおよびホワイトバランスの処理はスキップされる（1行のログメッセージが表示される）。一方、同じ実行内のM3C/ベイヤー画像については、これらの処理が適用される
* **ヴィネット補正**：画像全体にレンズのヴィネット補正を適用します
* **反射率キャリブレーション**：キャリブレーション係数を適用し、反射率値に変換します
* **指数計算**：植生指数（NDVI、NDRE、GNDVI、…）を計算します
* 出力：エクスポート可能な処理済み画像データ

このスレッドは GPU アクセラレーションの恩恵を最も受けやすく、[動的演算適応](dynamic-compute-adaptation.md) が調整対象となるスレッドです。

### スレッド 4: エクスポート

**目的**: 処理済みの画像をディスクに書き込みます。

* 選択された形式（`TIFF (16-bit)`、`TIFF (8-bit)`、 `TIFF (32-bit, Percent)`、`PNG (8-bit)`、`JPG (8-bit)`
* 出力ファイルにメタデータ（GPS、タイムスタンプ、処理パラメータ）を埋め込みます。これには、バージョン1.3.0以降、Survey3およびLATTICEのすべての処理モードで書き込まれる`Chloros:*`処理タグも含まれます
* 出力データをプロジェクトフォルダ内に「`<camera>/<format>/<Product>_Images/`」という形式で整理します（例：`LATT-M3M-L41-F550/tiff16/Reflectance_Calibrated_Images/`）。**エクスポートされたファイルはソースファイルの名前を保持し、フォルダ名がプロダクトを識別します。**
* LATTICEによる取得データの場合、1つのソースフレームから複数のプロダクト（デベイヤー処理済み、プレビュー、放射輝度、反射率、インデックス）が生成され、それぞれが独自のプロダクトフォルダに格納されます。インデックスプロダクトは、その実行で生成された反射率プロダクトから計算されます（反射率プロダクトが存在しない場合は、放射輝度など、その実行で生成された別のプロダクトから計算されます）。 マルチスペクトルM3Cカメラの放射輝度および反射率プロダクトには、`<format>/clamp_masks/`内にピクセル単位のクランプマスクが含まれる場合もあります（[出力画像フォーマット](../output-image-formats.md#clamp-masks)を参照）。
* 出力：ディスク上の最終ファイル

主にI/Oに制約されるスレッドであり、SSDストレージを使用すると処理速度が著しく向上します。

## 内部構造：エグゼキュータ

スレッド3内では、画像ごとの処理が次のように並列化されます：

* **GPU 戦略**(`GPU_SINGLE`、`GPU_PARALLEL`) では、**ワーカープロセス**のプールを使用します。各ワーカープロセスは独立した OS プロセスであり、独自の CUDA コンテキストを持っています。 Chlorosは、各ワーカーを起動する際、パッケージ化されたアプリケーション内ではワーカーの起動が機能しないPythonの`multiprocessing`を経由せず、インストール済みのバックエンドプログラムを再度起動することで各ワーカーを起動します
* **`CPU_PARALLEL`** はスレッドプール（Python の `ThreadPoolExecutor`）を使用します。NumPy と OpenCV は GIL を解放するため、スレッドだけで十分です
* 共有RAMが8GB以下のJetsonデバイスでは、エグゼキュータを完全に省略し、プロセス内で順次処理を行います
* VRAMが7GB未満のGPU上でのTexture Awareも順次実行されます。ノイズ除去モデルを複数回フィットさせることはできないためです

Chlorosは、Rayなどのサードパーティ製の分散フレームワークを一切使用しません。 戦略やワーカー数の選定方法については、[動的演算適応](dynamic-compute-adaptation.md)を参照してください。

## 順次処理とパイプライン処理

### フリーモード（順次処理）

Chlorosの無料版では、画像は**1枚ずつ**、4つのステージすべてを順次処理されます：

```

Image 1: [Detect] → [Calibrate] → [Process] → [Export]
                                                         Image 2: [Detect] → [Calibrate] → [Process] → [Export]
```

GUIには、無料モード用の簡略化された進行状況バーが表示されます。その順次処理のフェーズは、**ターゲット検出**、続いて**処理中**として表示されます。

### Chloros+ モード（パイプライン処理）

Chloros+ ライセンスでは、4つのスレッドすべてが異なる画像に対して**並行して**処理を行います：

```

Thread 1: [Image 1] [Image 2] [Image 3] [Image 4] ...
Thread 2:           [Image 1] [Image 2] [Image 3] ...
Thread 3:                     [Image 1] [Image 2] ...
Thread 4:                               [Image 1] ...
```

GUIの進行状況バーには4つのステージが表示されます。カーソルを合わせると、スレッドごとの進行状況を確認できます。CLIでは、同じ4つのステージが**Detecting、Analyzing、Processing、Exporting**としてリアルタイムで表示されます。

{% hint style="info" %}
**1つのラベル、2つの名称。** CLIでは、ステージ3を_Processing_と呼びます。一方、バックエンドのプレミアムモードの進行状況フィード（GUIの進行状況バーに表示されるもの）では、同じステージを_Calibrating_と表示します。これらは、同じスレッドが同じ処理を行っているものです（スレッド3：デベイヤー、補正、インデックス）。
{% endhint %}

{% hint style="success" %}
**Chloros+ によるパイプライン処理**は、ハードウェアやデータセットのサイズにもよりますが、順次処理に比べて 3～5 倍高速になる場合があります。 高速なGPUとSSDを搭載したシステムでは、処理速度の向上が最も顕著です。
{% endhint %}

## スレッド4のエクスポート進捗

エクスポートスレッドには独自の進捗追跡機能があり、これを個別にポーリングできます：

**CLI：**

```bash
chloros-cli export-status
```

**SDK：**

```python
status = chloros.get_status()
print(f"Export: {status['export']['percent']}% - Phase: {status['export']['phase']}")
```

スレッド4が100%に達した時点で処理は完了します。

{% hint style="info" %}
**画像が書き込まれなかった実行は失敗となります。**成功した場合、`chloros-cli process` は書き込まれた画像プロダクトの数 (`Image products written: N`) を報告します。 プロダクトが要求されたにもかかわらず、**1つも**書き込まれなかった場合（`project.json`および`calibration_data.json`のみが記録された場合）、CLIは`Processing finished but wrote no image products.`を出力し、**ゼロ以外の値で終了**します。 プロジェクトフォルダ名と一般的な原因（入力フォルダがキャプチャとして認識されなかった — レイアウトを確認し、`--input-level` — または要求されたすべてのプロダクトがそれらのカメラに適用不可能だった）を明示します。スクリプトはこの終了コードを信頼して処理できます。
{% endhint %}

## ダイナミック・コンピュート・アダプテーションとの関係

[ダイナミック・コンピュート・アダプテーション](dynamic-compute-adaptation.md) は主に **スレッド 3 (処理)** に影響を与えます：

* **`GPU_PARALLEL`**: スレッド 3 は、`fused_gpu` パイプラインを使用して、複数の画像を GPU 上で同時に処理します
* **`GPU_SINGLE`**: スレッド 3 は、`fused_gpu` またはメモリ効率に優れた `tiled_gpu` パイプラインを使用し、ワーカープロセスが I/O をオーバーラップさせる間、セマフォを用いて GPU アクセスをシリアル化します
* **`CPU_PARALLEL`**: スレッド 3 は、マルチスレッド並列処理を用いた CPU ベースの処理を行います

スレッド 1 および 2 が終了するにつれて、スレッド 3 の GPU メモリ割り当ても増加します — [動的 GPU メモリ割り当て](dynamic-compute-adaptation.md#dynamic-gpu-memory-allocation) を参照してください。
