# 処理パイプライン

Chloros1.2.0 では、段階的な組立ラインのように機能する 4 スレッドの処理パイプラインを採用しています。各スレッドがワークフローの異なるフェーズを処理するため、複数の画像が同時に異なる段階で処理中になることが可能です。

## パイプラインのアーキテクチャ

```

Images In → [Thread 1: Detection] → [Thread 2: Calibration] → [Thread 3: Processing] → [Thread 4: Export] → Files Out
```

すべての画像は、4つのスレッドすべてを順番に通過します。Chloros+のマルチスレッド処理では、複数の画像が同時に異なるスレッドで処理されます。つまり、スレッド3が1つの画像を処理している間、スレッド1は次の画像の検出を行い、スレッド2は別の画像のキャリブレーションを行い、スレッド4は処理完了した画像をディスクに書き込むといったことが可能です。

進行状況はスレッドごとに報告され、Server-Sent Events を通じてストリーミングされます（バックエンドは `/api/events` 上でこれらを公開します）。CLI のライブ進行状況表示では、4つの段階が **検出、分析、処理、エクスポート** とラベル付けされています。***

## スレッドの詳細

### スレッド1：検出

**目的**：画像を読み込み、キャリブレーションターゲットを検出します。

* ディスクから画像ファイルを読み込みます — Survey3 `.raw`+`.jpg`のペア、 LATTICE `.tif`/`.tiff`によるキャプチャ、および`.dng`
* EXIFメタデータ（GPS、カメラモデル、タイムスタンプ、露出）を抽出
* キャリブレーションターゲットを検出：LATTICEキャプチャ用のArUcoマーキング付きターゲット形状、およびSurvey3キャリブレーションターゲット写真用の従来のパネル検出器
* 出力：画像データ + メタデータ + ターゲット検出結果

主にI/OおよびCPUに依存するスレッド。

### スレッド 2：キャリブレーション

**目的**：検出されたターゲットからキャリブレーションパラメータを計算する。

* ターゲット画像から反射率キャリブレーション係数を算出
* ヴィネット補正パラメータを算出
* バンドごとのキャリブレーション曲線を決定
* 出力：各画像のキャリブレーションパラメータ

CPUに依存する計算スレッドです。反射率キャリブレーションが有効になっている場合、スレッド3はこのスレッドの完了を待機するため、画像の処理が始まる前に係数の準備が整います。

### スレッド 3: 処理 (GPU)

**目的**: 補正を適用し、植生指数を算出する。**これは最も計算負荷の高いスレッドである。*** **デベイヤー処理**: RAW ベイヤーデータをマルチチャンネル画像に変換する
  * 標準（高速、中品質） — デフォルト、`--debayer standard`
  * テクスチャ対応（低速、最高品質） — Chloros+ のみ、`--debayer texture-aware`、AI/ML ノイズ除去モデルを使用
  * LATTICE mono (M3M) での撮影はシングルバンドであるため、デモザイクおよびホワイトバランスの処理はスキップされます（1行のログメッセージが表示されます）。一方、同じ実行内の M3C/ベイヤー画像については、これらの処理が適用されます
* **ヴィネット補正**：画像全体にレンズのヴィネット補正を適用します
* **反射率キャリブレーション**：キャリブレーション係数を適用し、反射率値に変換します
* **インデックス計算**：植生インデックス（NDVI、NDRE、GNDVI、…）を計算します
* 出力：エクスポート可能な処理済み画像データ

このスレッドは GPU アクセラレーションの恩恵を最も受けやすく、[ダイナミック・コンピュート・アダプテーション](dynamic-compute-adaptation.md) が調整対象とするスレッドです。

### スレッド 4: エクスポート

**目的**: 処理済みの画像をディスクに書き込みます。

* 選択された形式（`TIFF (16-bit)`、`TIFF (32-bit, Percent)`、`PNG (8-bit)`、`JPG (8-bit)`）で出力ファイルを書き込みます
* 出力ファイルにメタデータ（GPS、タイムスタンプ、処理パラメータ）を埋め込みます
* 出力ファイルをプロジェクトフォルダ内に「`<camera>/<format>/<Product>_Images/`」という形式で整理します。例：`LATT-M3M-L41-F550/tiff16/Reflectance_Calibrated_Images/`。 **エクスポートされたファイルはソースファイルの名前を保持し、フォルダが製品を識別します。**
* LATTICE によるキャプチャの場合、1 つのソースフレームが複数の製品（デベイヤー処理済み、プレビュー、放射輝度、反射率、インデックス）に分岐し、それぞれが独自の製品フォルダに配置されます
* 出力：ディスク上の最終ファイル

主にI/Oに制約されるスレッド — SSDストレージを使用すると、処理速度が著しく向上します。

## 内部構造：エグゼキュータ

スレッド3内では、画像ごとの処理がPythonの標準的な`concurrent.futures`によって並列化されます：

* **GPU戦略**（`GPU_SINGLE`、`GPU_PARALLEL`）は、**spawn** 開始メソッドを持つ`ProcessPoolExecutor`を使用します。各ワーカーは独自のCUDAコンテキストを持つ独立したプロセスです（`fork`の場合、親プロセスの初期化済みのCUDA状態を継承してしまうため、子プロセスの状態が破損します）
* **`CPU_PARALLEL`** は `ThreadPoolExecutor` を使用 — NumPy および OpenCV は GIL を解放するため、スレッドだけで十分です
* 共有RAMが8GB以下のJetsonデバイスでは、エグゼキュータを完全に省略し、プロセス内で順次処理を行います
* VRAMが7GB未満のGPUでのTexture Awareも順次実行されます — ノイズ除去モデルは1回以上フィットできません

Chlorosは、Rayなどのサードパーティ製の分散フレームワークを一切使用していません。 戦略やワーカー数の決定方法については、[Dynamic Compute Adaptation](dynamic-compute-adaptation.md)を参照してください。

## 逐次処理とパイプライン処理

### フリーモード（逐次処理）

Chlorosの無料版では、画像は**1枚ずつ**、以下の4つの段階すべてを順次処理されます：

```

Image 1: [Detect] → [Calibrate] → [Process] → [Export]
                                                         Image 2: [Detect] → [Calibrate] → [Process] → [Export]
```

GUIには、無料モード用の簡略化された進行状況バーが表示されます。その順次処理段階は、**ターゲット検出**、続いて**処理中**として表示されます。

### Chloros+ モード（パイプライン処理）

Chloros+ ライセンスでは、4つのスレッドすべてが異なる画像に対して**並行して**処理を行います：

```

Thread 1: [Image 1] [Image 2] [Image 3] [Image 4] ...
Thread 2:           [Image 1] [Image 2] [Image 3] ...
Thread 3:                     [Image 1] [Image 2] ...
Thread 4:                               [Image 1] ...
```

GUIの進行状況バーには4つの段階が表示されます。カーソルを合わせると、スレッドごとの進行状況を確認できます。CLIでは、同じ4つの段階が**「検出中」、「分析中」、「処理中」、「エクスポート中」**としてリアルタイムでストリーミングされます。

{% hint style="info" %}
**1つのラベル、2つの名称。** CLIでは、ステージ3を_Processing_と呼んでいます。一方、バックエンドのプレミアムモードの進行状況フィード（GUIの進行状況バーに表示されるもの）では、同じステージを_Calibrating_と表示しています。これらは、同じスレッドが同じ処理を行っているものです（スレッド3：デベイヤー、補正、インデックス）。
{% endhint %}

{% hint style="success" %}
**Chloros+ によるパイプライン処理**は、ハードウェアやデータセットのサイズにもよりますが、順次処理に比べて3～5倍高速になる場合があります。 高速なGPUとSSDを搭載したシステムでは、処理速度の向上が最も顕著です。
{% endhint %}

## スレッド4のエクスポート進捗

エクスポートスレッドには独自の進捗追跡機能があり、個別にポーリングすることができます：

**CLI:**

```bash
chloros-cli export-status
```

**SDK:**

```python
status = chloros.get_status()
print(f"Export: {status['export']['percent']}% - Phase: {status['export']['phase']}")
```

スレッド4が100%に達すると、処理が完了します。

{% hint style="info" %}
**画像が書き込まれなかった実行は失敗となります。**成功した場合、`chloros-cli process`は、書き込まれた画像プロダクトの数（`Image products written: N`）を報告します。 プロダクトが要求されたにもかかわらず、**1つも**書き込まれなかった場合（`project.json`および`calibration_data.json`のみが記録された場合）、CLIは`Processing finished but wrote no image products.`を出力し、**ゼロ以外の値で終了**します。 プロジェクトフォルダ名と一般的な原因（入力フォルダがキャプチャとして認識されなかった — レイアウトを確認してください、および `--input-level` — あるいは要求されたすべての製品がそれらのカメラに適用できなかった）が表示されます。スクリプトは終了コードを信頼することができます。
{% endhint %}

## ダイナミック・コンピュート・アダプテーションとの関係

[ダイナミック・コンピュート・アダプテーション](dynamic-compute-adaptation.md) は主に **スレッド 3 (処理)** に影響を与えます：

* **`GPU_PARALLEL`**: スレッド 3 は、`fused_gpu` パイプラインを使用して、複数の画像を GPU 上で同時に処理します
* **`GPU_SINGLE`**: スレッド 3 は、`fused_gpu` またはメモリ効率に優れた `tiled_gpu` パイプラインを使用し、ワーカープロセスが I/O をオーバーラップ処理する間、セマフォを用いて GPU アクセスをシリアル化します
* **`CPU_PARALLEL`**: スレッド 3 は、マルチスレッド並列処理を用いた CPU ベースの処理を行います

スレッド1および2が終了するにつれて、スレッド3のGPUメモリ割り当ても増加します — [動的GPUメモリ割り当て](dynamic-compute-adaptation.md#dynamic-gpu-memory-allocation)を参照してください。
