# 処理の完了

Chlorosによる処理が完了したら、結果を確認し、出力品質を検証し、ワークフローで使用するよう処理済みの画像を準備します。このページでは、最終手順と次のアクションについて解説します。

## 処理完了の表示

処理が正常に完了すると、以下の表示が現れます：

* ✅ **進行状況バー**：100% 完了
* ✅ **デバッグログ**：最後の `[RUN-SUMMARY]` 行に、各項目（画像数、カメラグループ数、ターゲット数、キャリブレーション済み画像数、書き込み済みファイル数）のカウントが表示されます
* ✅ **開始ボタン**：再び有効になります（次の処理実行の準備が整います）
* ✅ **出力ファイル**：処理済みのすべての画像がプロジェクトの出力ツリー（以下）に保存されます

{% hint style="warning" %}
**画像が書き込まれなかった実行は失敗となります。** 画像プロダクトを要求したにもかかわらず、実行で何も書き込まれなかった場合、Chlorosはそれを失敗として報告します。ログ名に含まれる「`[RUN-SUMMARY]`」は、その原因として考えられる事項（インポートされたデータがない、ターゲットが検出されなかった、または要求されたすべてのプロダクトが適用不可としてスキップされた）を示唆しています。CLIでの同等の処理は、非ゼロの終了コードで終了します。 意図的にメタデータのみを生成する実行（すべてのエクスポート製品をオフにし、インデックスを作成しない）は、成功とみなされます。[CLIリファレンス](../reference/cli-reference.md#a-run-that-writes-no-images-fails)を参照してください。
{% endhint %}

## 処理済み画像の場所

### 出力フォルダの開き方

1. **メインメニュー** <img src="../.gitbook/assets/image (1) (1) (1) (1).png" alt="" data-size="line">
アイコン（左上）をクリックします
2. **「プロジェクトフォルダを開く」** を選択します
3. ファイルエクスプローラーがプロジェクトディレクトリを開きます
4. プロジェクト名を基にプロジェクトを探します

### 出力ツリー

出力ファイルは、**プロジェクトフォルダの下に、カメラごとにグループ化され、さらにファイル形式ごとに分類されて**保存されます：

```
<project>/
└── LATT-M3M-L41-F550/                  # one folder per camera
    ├── tiff16/
    │   ├── Reflectance_Calibrated_Images/
    │   ├── Debayered_Images/
    │   ├── Preview_Images/
    │   └── NDVI_Index_Images/           # one folder per selected index
    └── tiff32/
        └── Radiance_Images/             # float32 radiance always lands here
```

* **カメラフォルダ**：LATTICEの場合は `LATT-<sensor>-<lens>-F<filter>` （キャプチャの EXIF 情報 `Model` と一致）、Survey3の場合は `<model>_<filter>`（例：`Survey3N_RGN`）。 センサーとフィルターを共有するがレンズが異なる2台のカメラは、別々のツリーを保持します。ヴィネット、視野、歪みが異なるためです。
* **フォーマットフォルダ**：エクスポート形式の設定に従います — `tiff16`、`tiff8`、`png8`、`jpg8`、 または、TIFF（32ビット、パーセント）の場合は `tiff32`。 ラディアンスは常にfloat32形式であり、常に`tiff32`に保存されます。
* **出力フォルダ**:
  * `Reflectance_Calibrated_Images/` — キャリブレーション済み反射率
  * `Debayered_Images/` — 線形デベイヤー処理済み（LATTICE）：ダークオフセットが除去され、デモザイク処理が施されています。フラットフィールド補正やアンミックス処理は行われておらず、センサーのネイティブ方向で保存されています
  * `Preview_Images/` — 表示用プレビュー (LATTICE)
  * `Radiance_Images/` — float32 スペクトル放射輝度、W/m²/sr/nm (LATTICE マルチスペクトル)
  * `Vignette_Corrected_Images/` **または** `Sensor_Response_Images/` — 反射率リファレンスがないフレームに対する、キャリブレーションされていないフォールバックデータ。1回の実行につき、これら2つのうち正確に1つが存在し、ヴィネット補正設定によって選択される
  * `<INDEX>_Index_Images/` — 選択されたインデックスごとに1つのフォルダ（例：`NDVI_Index_Images`）
* **`clamp_masks/`**（バージョン 1.3.0 から追加、LATTICE マルチスペクトル M3C カメラのみ）：放射輝度または反射率プロダクトにおいて、バンドのアンミックス処理によりクリップされた負の値がゼロに切り詰められた場合、プロダクトフォルダとは別にフォーマットフォルダ内に生成されます。 このフォルダには、影響を受けたプロダクトごとに 1 ピクセルごとのマスクが 1 つ格納されます（例：`tiff16/clamp_masks/Reflectance_Calibrated_Images/<name>_clampmask.tif`）。マスクはプロダクトフォルダ内には決して格納されないため、プロダクトフォルダはそのまま写真測量ソフトウェアに渡すことができます。 [クリップマスク](../output-image-formats.md#clamp-masks)を参照してください。

{% hint style="info" %}
**エクスポートされたすべてのプロダクトは、ソースファイルの名前を保持します。**`capture_..._raw.tif` の放射輝度データとしてエクスポートされたファイルは、依然として `capture_..._raw.tif` という名前ですが、実際には `tiff32/Radiance_Images/` フォルダ内に格納されています。**フォルダが製品を識別するものであり、ファイル名**ではないため、`*radiance*.tif`を検索しても何も見つかりません。代わりにディレクトリで一致させる必要があります。
{% endhint %}

### ファイル数はどれくらいになるべきか？

数式で計算しないでください — 出力ファイルの数は、どの製品が有効化されていたか、および各カメラにどの製品が適用されるかによって異なります（例：RGBカメラには放射輝度/反射率のデータは生成されません）。 正確なファイル数はログに記載されています。最後の「`[RUN-SUMMARY]`」行には、書き込まれたファイル数が正確に報告されており、ヒント行にはスキップされた項目についての説明が記載されています。

## 反射率ピクセル値の読み取り (GIS / Pix4D / スクリプト)

反射率は整数のDNとして保存されており、**ρ = 1.0 に対応するDNは、使用したカメラによって異なります**：

| ソース          | ρ = 1.0 に対応する値 | 判別方法                                        |
| --------------- | ---------- | -------------------------------------------------- |
| LATTICE (M3C/M3M) | **32768** (ρ 2.0 までの余裕あり) | ファイルに XMP タグ `Chloros:PixelScale=32768` が付与されている |
| Survey3          | **65535**（ρ 1.0でクリップ）     | `Chloros:PixelScale`タグなし — その欠如が合図となります（Survey3製品には他の`Chloros:*`処理タグが含まれています） |

**`Chloros:PixelScale`タグを読み取り、その値で割る**こと。一律に65535と仮定してはならない — LATTICE反射率を65535で割ると、すべての値が黙って半分になってしまう。 バージョン1.3.0より前の8ビット形式で書き込まれた反射率ファイルは、リスケールされずにクリップされており、スケールタグもありません。そのため、値を割るのではなく、16ビットまたは32ビットで再エクスポートしてください。 詳細については、[出力画像フォーマット](../output-image-formats.md)を参照してください。***

## エクスポート時に引き継がれるメタデータ

すべての出力ファイルには、ソース画像の**GPSブロック**とその**EXIFサブIFD**が保持されるため、
エクスポート時には `FocalLength`、`FNumber`、`ExposureTime`、 `ISO`、`DateTimeOriginal`、および
`CameraSerialNumber`が、地理参照情報とともにエクスポートされます。

{% hint style="warning" %}
**オルソモザイクの縮尺が不自然な値になった場合は、まず `FocalLength` を確認してください。**
Pix4Dは、焦点距離と高度から地上サンプル距離を算出します。このタグがない場合、
著しく誤った縮尺になってしまいます。ある49枚の撮影データから構成されるフライトでは、411 m × 160 mの
のオレンジ畑が47.8 km × 13 kmとして再構築され、大部分が
空白の領域で構成される455メガピクセルのオルソ画像が生成されてしまいました。タイリングの遅さや予想外に巨大なファイルサイズは、これに伴う症状であり、別の
問題ではありません。

```bash
exiftool -FocalLength -GPSLatitude "YourProject/.../some_export.tif"
```
{% endhint %}

*すべての*タグがコピーされるわけではありません。IFD0の構造タグは意図的に除外されています（これらを
コピーするとLATTICEの出力が破損します）。また、`ExifImageWidth` / `ExifImageHeight`は、
元のキャプチャを記述しているため除外されます。これらが含まれていると、サイズ変更されたエクスポートが、
自身のラスタと矛盾する寸法を主張してしまうことになるからです。

Chlorosはまた、各プロダクトに対してどのような処理が行われたかを記述する独自の`Chloros:*` XMPタグも書き込みます
（例：`Chloros:ProcessingLevel`、`Chloros:CalibrationApplied`、
`Chloros:VignetteCorrected`）。バージョン1.3.0以降、Survey3の製品はすべての処理
モードでこれらを含んでいます。インデックス製品は、ソースの生データのタグを繰り返し記載するのではなく、
インデックス自体（`Chloros:ProcessingLevel=index`）、
計算式、およびそれが反射率から計算されたか放射度から計算されたかを記述しており、260文字を超える深さのフォルダ内にある製品もメタデータを
保持しています。詳細は [出力画像フォーマット](../output-image-formats.md#index-products)を参照してください。

## よくある出力に関する問題と解決策

### 問題：出力ファイルがない

**考えられる原因：**

* そのカメラには該当するプロダクトがない（例：RGBカメラ用の放射輝度/反射率 — ログにその旨が記載されている）
* 必要な参照情報が欠落していた（例：ターゲットおよび`.daq`のダウンウェリングがない状態での反射率）
* プロジェクト設定で、プロダクトのエクスポートチェックボックスが無効になっていた
* エクスポート中にディスク容量が不足した

**解決策：**

1. デバッグログ内のヒント（`[RUN-SUMMARY]`）および行（`[EXPORT-CHECK]`）を確認してください。これらはカメラごとのスキップについて説明しています
2. [プロジェクト設定](adjusting-project-settings.md)内のエクスポート対象製品のチェックボックスを確認してください
3. ディスク容量が十分であったか確認してください
4. 原因を修正した後、再処理を行ってください

### 問題：エッジが暗い、または明るい（ヴィネットが依然として目立つ）

**考えられる原因：**

* ヴィネット補正が無効になっている
* カメラ／レンズがChlorosプロファイルデータベースに登録されていない
* 補正能力を超える極端なヴィネット

**解決策：**

1. [プロジェクト設定](adjusting-project-settings.md)でヴィネット補正が有効になっていることを確認する
2. カメラモデルが正しく検出されているか確認する
3. ヴィネットが残る場合は、MAPIRサポートに連絡する

### 問題：色や値が不正確

**考えられる原因：**

* キャリブレーションターゲットが検出されていない
* 誤ったキャリブレーションターゲットモデルが選択されている
* 反射率キャリブレーションが無効になっている
* ターゲット画像の品質が低い

**解決策：**

1. 反射率キャリブレーションが有効になっていることを確認する
2. デバッグログの「ターゲット検出」メッセージを確認してください
3. ターゲット画像の品質を確認してください
4. 適切なターゲットをマークして再処理してください

### 問題：NDVIの値が不正確に見える

**想定されるNDVIの範囲：**

* **水、岩石、土壌**：-0.1～0.2
* **まばらな／不健全な植生**：0.2～0.4
* **中程度の植生**：0.4～0.6
* **健全で密生した植生**：0.6 ～ 0.9**値がこれらの範囲外の場合：**

1. 反射率キャリブレーションが適用されていることを確認する
2. 光センサーのログが含まれていることを確認する
3. キャリブレーションターゲットが検出されたことを確認する
4. 正しいカメラモデルが検出されていることを確認する
5. ターゲット画像の撮影タイミングと条件を確認してください
6. 反射率ファイルからインデックスを独自に算出する場合は、ファイルの `Chloros:PixelScale`（上記参照）で除算したことを確認してください

## 処理済み画像の使用

### 写真測量／オルソモザイク作成用

**推奨ワークフロー：**

1.**キャリブレーション済みの反射率画像を** 写真測量ソフトウェアにインポートする：
   * Pix4Dmapper
   * Agisoft Metashape
   * DroneDeploy
   * WebODM
2. **EXIFメタデータを保持する**：ジオタグ付けのためにGPSデータが保存されていることを確認してください
3. **キャリブレーション済みワークフロー**：科学的精度を確保するために反射率画像を使用してください。LATTICEの反射率画像には、Pix4Dが読み取れるXMPキャリブレーションタグが含まれています
4. **インデックスモザイクを処理する**：個々のインデックス画像からNDVIオルソモザイクを作成します
5. **地理参照付きGeoTIFFをエクスポート**：GISアプリケーションでの使用向け

### GIS解析用

**推奨ワークフロー：**

1.**QGIS、ArcGIS、または類似のソフトウェアに読み込む**

2.**マルチバンド解析には16ビットTIFF**の反射率画像を使用（ファイルの`Chloros:PixelScale`で除算）
3. **インデックス画像**（NDVI、NDRE）を、そのまま使用可能な植生レイヤーとして活用
4. **ラスタ計算機**：カスタム分析のためにバンドを組み合わせる
5. **エクスポート**：分類マップ、変化検出、植生健全性マップを作成する

### 直接分析／レポート作成用

**推奨ワークフロー：**

1.**LUTカラーが適用されたインデックス画像**を視覚的なレポートに使用する
2. **統計値の抽出**：圃場／区画ごとのNDVI平均値
3. **時系列分析**：複数の観測セッションにわたる指標の比較
4. **レポートの作成**：地図、統計値、可視化データを盛り込む***

## アーカイブとバックアップ

### 推奨されるバックアップ戦略

**保存すべきもの：**

* ✅ **元のRAW/JPG画像またはLATTICEのRAWキャプチャ** - 別のドライブまたはクラウドにアーカイブする。RAWデータはパイプラインのソースであり、それ以外のデータはすべてそこから再生成可能
* ✅ **`.daq` / `.csv` 光センサーファイル** - 後で反射率を再算出するために必要
* ✅ **処理済み出力** - キャリブレーション済みの画像と指標を保存
* ✅ **プロジェクトフォルダ**（`project.json` および関連ファイル） - 必要に応じて再処理を行うためのすべての設定が含まれています
* ✅ **デバッグログ** - 処理の詳細を記録します
* ✅ **キャリブレーションターゲット画像** - 検証および再処理用

**保存に関する推奨事項：**

* **直後のバックアップ**：外付けハードドライブ
* **長期保存**：クラウドストレージ（Google Drive、Dropbox など）
* **重要データ**：異なる場所に 2～3 部のコピーを保管する***

## 後処理のトラブルシューティング

### 設定を変更して再処理する

結果が満足のいくものでない場合：

1. 元の画像を保存しておく（絶対に削除しない）
2. Chlorosで同じプロジェクトを開く3. 「プロジェクト設定」パネルで設定を調整する
4. 再度処理を行う — 出力は同じ出力フォルダに保存されるため、前回の実行で生成された同名のファイルは上書きされる

### 画像の一部のみを処理する

特定の画像のみを再処理するには：

1. 新しいプロジェクトを作成する
2. 再処理が必要な画像のみをインポートする
3. 同じ設定テンプレートを使用する
4. より小規模なデータセットを処理する
